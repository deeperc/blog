Three bugs that passed ERC

Nelson Gaspard and Michael King

Earlier this year I filed three issues against production open-hardware designs, three findings across two organizations and three repositories. Each one is a real electrical defect, and each one passed KiCad's ERC.

An ID EEPROM with SDA and SCL swapped. On Antmicro's Jetson AGX Thor baseboard, the AT24CS01 ID EEPROM has its I²C pins crossed, with SDA wired to the bus's SCL net and SCL wired to the SDA net. The other two devices on the same bus are wired correctly, and the library symbol itself is correct, which localizes the defect to the wiring at that one part rather than a library error. On fabricated boards, identification over that bus fails. The defect survived a commit dedicated to ERC and DRC cleanup, and the report became the repository's first issue.

Four 1.8 V flash chips on a 3.3 V rail. On Antmicro's Artix DC-SCM, four W25Q32JW SPI-NOR flash parts have VCC on the 3.3 V rail. The JW is Winbond's 1.8 V line, with an absolute maximum of 2.5 V. Git history shows the design originally used the W25Q32JV, which is the 3.3 V variant. A later commit, titled "Fix schematic ERC errors. ERC clean," changed the part to the JW. The commit that made the schematic ERC-clean is the commit that introduced a real overvoltage.

An I²C bus crossed at the root sheet. On Tronex's TRNXSDR Zynq SDR carrier, the management microcontroller drives its SCL onto the SDA pins of both devices on one of its I²C buses, a PMIC and a clock generator, and vice versa. The board conveniently contains its own control group: the sibling bus uses the same parts, the same symbols, and the same sub-sheets, wired correctly. Per the PMIC's datasheet its SCL pin is input-only, so as drawn the device cannot ACK, and that bus is non-functional. The board still boots on the PMIC's OTP defaults, which is exactly the kind of failure that hides until someone needs runtime PMIC or clock control.

All three are filed upstream with full evidence. Current status is tracked in FINDINGS.md, where the issue links are public and you can judge the evidence yourself.

These three findings share a property: none of them is a structural error. A crossed net label is an electrically legal connection. A rail hookup is valid to ERC regardless of what the connected part is rated for. Catching this class of defect requires knowing what each pin is for and what each part tolerates. That is datasheet knowledge, not netlist structure, and it is the class of defect DeepERC targets.

The checks themselves are fairly straightforward once the specifications exist. The engineering problem worth writing about is how the tool obtains those specifications with a language model without ever letting the model decide a verdict.

What DeepERC is

DeepERC is an open-source (Apache-2.0) checker for KiCad designs. You export a netlist, point the tool at it, and it cross-references every net against electrical specifications derived from the parts' datasheets. It currently ships seven check families: signal-level compatibility, supply overvoltage, structural integrity, peripheral pin-role coherence and bus capability, pull-up value, pull-up presence, and output-conflict detection.

The pipeline uses an LLM only in the places where nothing else works: reading datasheets, resolving ambiguous part names, classifying ambiguous net names, and writing human-readable explanations. Everything a verdict depends on is deterministic.

This split was not a design philosophy I started with. It is a pattern that emerged four separate times during development, each time because a documented failure forced it.

The four-instance pattern

The rule, as it eventually crystallized: any LLM output that flows toward a verdict passes a deterministic plausibility check before anything consumes it. The model supplies evidence. The deterministic layer decides.

It is important to note that this is not a novel idea. It is closely related to verifier-in-the-loop approaches and to any system that pairs a generative model with a symbolic checker. What I can offer is a case study: four independent places where the pattern emerged in one small tool, the specific failure each instance prevents, and the measured outcome.

Instance 1, part resolution. Early in development, the resolver silently fell back to a wrong datasheet when it could not find the right one, and the checker evaluated a 74HC595 against another part's specifications. The fix was not a better prompt. The fix was deterministic matching first (strip the package suffix, then exact-match against the datasheet set), with the LLM consulted only for genuinely ambiguous names, and its answer validated against the files actually on disk before use. The same shape recurred later with supplier APIs. A fuzzy keyword search is useful for finding candidates, but an exact match on the returned part number is mandatory before anything downstream trusts the result.

Instance 2, specification extraction. This is where the pattern earned its keep. The extraction model was given a datasheet whose absolute maximum ratings table had been rendered as an image placeholder by the PDF converter, so the table was simply absent from its input. The model did not report that the table was missing. It produced 6.0 V for a part whose real limit is 4.0 V, a plausible, wrong, verdict-corrupting number. Prompt engineering does not fix this failure mode, because the model cannot extract what is not in its input but will confidently produce something that looks extracted. What fixes it is upstream input validation, which detects the missing table region, re-extracts it with a second parser, and patches it into the input, combined with a downstream deterministic validator that scores every extracted pin group for completeness and plausibility. The validator also flags telltale artifacts, such as an input-high threshold equal to the absolute maximum, which is the signature of a single-table extraction failure.

Instance 3, power-net inference. The first version handed the entire netlist to the model and asked which nets were power rails. On a 192-pin design this hung. Worse, borderline classifications came back different from run to run, and that non-determinism cascaded through every downstream check. The replacement is deterministic-first. A rule tier classifies the large majority of rails instantly from their names, the model sees only the ambiguous remainder, and every inferred rail is tagged with its source, rule-derived or model-inferred, so a human can audit and correct it. The runtime went from hanging overnight to minutes, and the run-to-run variance went with it.

Instance 4, explanations. In an early version, the model's explanation of a violation described the violation backwards. The verdict was right and the prose was inverted. That was the last time generated text sat anywhere load-bearing. In the shipped tool, the verdict, the numbers, the severity, and the evidence label are all computed deterministically, and the model writes one sentence of explanation about a finding that has already been decided. A wrong sentence is now an annoyance rather than a wrong answer.

Three model failure modes drove all four instances, and they are worth naming because they generalize. Small models fabricate plausible values when the input lacks the answer. They do not reliably honor numeric constraints even when the constraints are explicitly stated. And they are non-deterministic from run to run on borderline calls, which cascades through downstream logic. In every case the durable mitigation was deterministic: input validation, plausibility gates, and post-processing guards, never prompt tuning.

One payoff is worth measuring directly. The extraction model has since been swapped entirely, from a local 4-billion-parameter model to a hosted one, without touching a single verdict rule. The bounds are what make a model swap uneventful, which is what a model swap should be. Extraction is also a one-time cost. Results are cached per part, keyed on a hash of the source datasheet, and re-extracted only if the PDF itself changes. The corpus-wide extraction bill was a few dollars, once.

The third finding above is this architecture's best witness. The Tronex bus crossing was flagged with an empty knowledge base for every part involved. There were no curated entries, and the verdict came from pin-function evidence in the netlist plus the vendor datasheet. The deterministic layer produced the finding. The model only ever read the PDF.

UNRESOLVABLE is an answer

The second load-bearing design decision: when the tool lacks the data to make a verdict, it says so. UNRESOLVABLE is a first-class status. It is not a failure, it is not silence, and it is never a default PASS.

The alternative is worse than it sounds. A checker that quietly skips what it cannot evaluate produces clean-looking reports that mean "no violations found among the things I did not tell you I skipped." A null value that propagates into a PASS is a misleading clean result. DeepERC instead produces an honest to-do list. In the current release, every UNRESOLVABLE finding names the endpoint it could not resolve and the specific reason, which part and which missing piece of evidence, so an unresolvable net becomes an actionable line item rather than an unexplained gap.

Every finding that is resolvable carries an evidence label, byte-identical to what the code emits:

  • Confirmed — §X.Y means the limit was verified against a local copy of the datasheet, with the section cited.
  • Cache-sourced — §X.Y (not locally verified) means the specification comes from the shipped extraction cache and you do not have the PDF locally.
  • Cache-sourced — §X.Y (local datasheet differs from cache source) means your local PDF does not hash-match the one the cache was built from, and the report says so.
  • Assumed means the value was inferred, for example a rail voltage from a net name, and the finding tells you it was.

The cache itself is listed part by part, with source hashes, in an integrity-hashed manifest. The point of this ceremony is a correction loop. When someone disputes a finding, the label tells both of us exactly which piece of evidence to check, so a false-positive report becomes a fix rather than an argument.

Checks we shipped only in part

Some checks ship in a reduced form, and the reasons are as instructive as the checks that ship whole.

The clearest case is UART. The obvious idea is to detect TX to RX swaps the way the tool detects SDA to SCL swaps, and doing that from net names alone is not possible.

The tool checks a connection by matching the possible roles of the pins that share a net. I²C coherence works because a correct I²C bus is built on agreement: every device presents SDA to the SDA net, so a pin whose roles include SDA, sitting on a net of SDA pins, confirms the wiring, and a clock-only pin on that net condemns it. UART is complementary rather than shared. A correct link puts one device's TX on the other device's RX, so agreement between the endpoints is exactly what a correct board does not show, and the net label, written from one device's point of view, tells you which end named it rather than whether the wiring is right.

There is a second gap on most real boards: the UART heads to a connector, and connectors do not carry datasheet pin roles today, so the tool cannot see the far end of the link at all.

So what ships is the part of the check the evidence supports. A line wired into a pin with no UART function at all is flagged. A swap that ties two drivers together is a different kind of defect, and it can fall to a different family: two driven outputs on one net is an electrical conflict regardless of protocol, and the output-conflict check looks for exactly that, provided the pins declare themselves as outputs rather than as bidirectional. The genuinely silent case is a swap that leaves two receivers listening to each other. Nothing drives the net, there is no conflict to see, and the link is simply dead. That case produces no finding rather than a guess. The fuller check is reachable: role assignments for connectors would let the tool stand at both ends of many links, though a connector's TX and RX depend on which side of the link the connector speaks for, so the convention has to be established per design rather than assumed. Until that exists, the gap is documented in LIMITATIONS.md rather than left for users to discover.

That is the standard throughout. A check ships when it can carry evidence for its verdicts, and it ships smaller when the rest would be guesswork.

How it is measured

Precision is gated on every change. Each change runs against a fixed 126-board regression set of real KiCad designs and is compared finding by finding against the previous baseline, so new findings must be explained and regressions cannot land silently. Recall is measured against a frozen mutation corpus of 218 known-bad netlists, deterministic and seed-pinned, each injecting a defect class the tool checks today, such as swapped bus lines, wrong-voltage parts, and missing pull-ups, into a known-good design. A MISS and an UNRESOLVABLE are different failures with different fixes. An UNRESOLVABLE means the tool could not obtain the evidence needed to evaluate the mutant at all, and it is the same first-class status described earlier rather than a hidden zero. A MISS means the tool had the evidence to evaluate the mutant, ran the check, and still produced nothing, and finding out why is the current investigation. Mutants that could not be fairly evaluated, such as degenerate generator artifacts and cases undetectable by design, are excluded from evaluation, and the table reports the remainder.

The supply row is the weak one, at 8 of 19, and I am publishing it as measured. The current misses share one property: in every case the detector produced no finding at all rather than a wrong verdict, and the misses concentrate in supply-rail mutations on a small set of boards, which localizes the work. Two check families have detectors but no mutation operators yet, so the table measures five of the seven families. It is important to note that mutant counts per family are artifacts of the generator and its seed pool, and they carry no claim about which defect classes matter most.

The numbers point at two pieces of work: the supply family, where the misses and nearly all of the UNRESOLVABLE results sit, and detectors for the defect classes that do not yet have one.

The corpus itself does not ship with the repository, because it is built from other people's designs and redistributing them is not mine to do. The methodology is documented in CORPUS.md. The three findings at the top of this post are the same defect classes appearing in the wild.

What it does not do

DeepERC complements ERC. It does not replace it, and you should run both. Coverage is bounded by the knowledge base and the extraction cache, so parts the tool has no evidence for come back UNRESOLVABLE rather than silently passed. Some checks are scoped narrowly on purpose, and peripheral role coverage varies by MCU family. The full, current list of limitations, including the release-specific ones, lives in LIMITATIONS.md, and it is maintained with the same care as the feature list, because a limitations file that flatters the tool is not documentation.

Try it

The repository is at github.com/deeperc/deeperc, current release v0.2.1. It requires Python 3 and git. The examples/ directory contains ready-to-run boards with known defects, including an I²C swap and an SPI swap the tool catches, and the README walks through them. If you run it on a real board and it misses something, that is exactly the report I want. File an issue with the netlist detail, and the finding either becomes a check or an honest entry in LIMITATIONS.md.
